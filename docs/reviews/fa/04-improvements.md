# بازنگری بهبودها ZCES — افزودن / حذف / نکات پایش

**تاریخ:** ۲۰۲۶-۰۸-۲۹ · **زبان:** فارسی (نسخه انگلیسی: `docs/reviews/en/`)
**پرسش بازنگری‌شده:** برای بهبود پیاده‌سازی چه چیز دیگری باید انجام شود؟ آیا چیزی باید اضافه یا حذف شود؟

## ۱. افزودنی‌ها (فراتر از متن نیازمندی‌ها)

### استحکام امنیتی (الان ارزان، بعداً گران)
- **قفل حساب + سیاست رمز عبور** — محدودسازی تلاش ناموفق به ازای حساب/IP پیش از وجود Rate Limiting؛ توافق بر هزینه bcrypt در فاز ۲.
- **تشخیص استفاده مجدد از Refresh Token** — چرخش از قبل الزامی است؛ تشخیص استفاده مجدد از توکن چرخیده باید کل خانواده توکن‌ها را باطل کند (نشانه سرقت توکن).
- **Security Headerها** — CSP، X-Frame-Options: DENY، HSTS (محیط عملیاتی)، Referrer Policy؛ راستی‌آزمایی در فاز ۱۰.
- **خروج همه‌جا (Logout Everywhere)** — باطل‌سازی همه Refresh Tokenها هنگام تغییر رمز عبور (با ثبت Audit).

### تجربه توسعه و کیفیت
- **Pre-commit Hookها** — ruff + mypy (بک‌اند)، eslint + prettier (فرانت‌اند)، detect-secrets؛ نصب در فاز ۱ و اجرا در CI از فاز ۱ به بعد.
- **اجرای تک‌فرمانی** — `scripts/dev.ps1` بک‌اند، فرانت‌اند و Celery را اجرا و سلامت Postgres/Redis را بررسی می‌کند؛ `scripts/seed-dev.ps1` برای Seed توسعه Idempotent. این مستقیماً هدف کارفرما (اجرای شخصی برنامه) را پشتیبانی می‌کند.
- **Seed توسعه با Faker** — داده نمونه واقع‌گرایانه دوزبانه (کارکنان، کاتالوگ، موجودی، وام) تا هر صفحه UI بدون ورود دستی داده قابل نمایش باشد.

### مشاهده‌پذیری و صحت
- **/healthz و /readyz** — تفکیک Liveness و Readiness (بررسی DB + Redis)؛ استفاده توسط systemd و Nginx.
- **Prometheus /metrics** — تأخیر درخواست، نرخ خطا، عمق Outbox، اتصال‌های SSE؛ داشبوردهای Grafana پس از v1 اختیاری می‌مانند.
- **بسته E2E با Playwright** — تست دودی مرورگری سناریوهای حیاتی §27.3 (ورود، ایجاد کارمند، درخواست کالا تا Fulfillment، اعتبارسنجی وام، اعلان زنده) در هر دو زبان شامل اسکرین‌شات RTL.

### پرداخت محصول
- **حالت‌های خالی/خطا/بارگذاری به‌عنوان UI درجه یک** — هر صفحه لیست از روز اول دارای Skeleton، حالت خالی و حالت خطا (دوزبانه) باشد.
- **UX قفل‌گذاری خوش‌بینانه** — خطاهای STALE_VERSION به‌جای خطای خام، دیالوگ دوستانه «داده تغییر کرده، بازگذاری کنید» نمایش دهند.
- **کامپوننت انتخاب تاریخ جلالی/میلادی** — مشترک بین همه فرم‌ها؛ هرگز در هر صفحه جداگانه ساخته نشود.

## ۲. حذف / تعویق (نسخه اول چابک بماند)

| مورد | تصمیم | دلیل |
|---|---|---|
| لایه ابر (06) | حذف | VM داخلی؛ Config مبتنی بر Environment قابلیت انتقال را حفظ می‌کند |
| Load Balancer / چندگرهی (11) | حذف | یک VM کافی است؛ طراحی Stateless گزینه را باز نگه می‌دارد |
| CDN | حذف | برنامه Intranet — لبه عمومی ندارد |
| RLS بومی PostgreSQL | تعویق | فیلتر Scope در سطح برنامه به هر حال الزامی است؛ در صورت تغییر مدل تهدید بازبینی شود |
| Tracing کامل OpenTelemetry | تعویق | همبستگی trace_id (فرانت↔بک↔Worker) نیازمندی مشاهده‌پذیری را با کسری از هزینه عملیاتی برآورده می‌کند |
| داشبوردهای Grafana | تعویق | فعلاً Metrics پرومتئوس؛ داشبوردها پس از v1 |
| Docker | تعویق (طبق نیازمندی‌ها §33) | صراحتاً پس از پایدارسازی Local/VM برنامه‌ریزی شده |
| کانال Email | تعویق | v1 فقط In-app + SSE (هوک Email پشت Outbox آماده می‌شود) |

## ۳. موارد پایش / ریسک‌ها

1. **لایسنس فونت** — FontLicense.txt باید کنار فونت‌ها منتشر شود؛ کد ۶ رقمی لایسنس FontIran در صورت وجود وارد شود (جایش فعلاً خالی است).
2. **وابستگی Redis** — روی این ماشین نصب نیست؛ تصمیم WSL2 گرفته شد. راه‌اندازی فاز ۱ شامل نصب و راستی‌آزمایی `redis-cli ping` است. توزیع SSE و Celery هر دو به آن وابسته‌اند — اجازه ندهید فاز ۸ بدون آن برسد.
3. **PostgreSQL 18 در برابر «16+»** — نیازمندی را برآورده می‌کند، اما خروجی Autogenerate آلنبیک باید در هر Migration بازبینی شود (ایندکس‌های جزئی، ستون‌های UUID) — در backend/AGENTS.md مقرر شده است.
4. **Scope Resolver ریسک شماره یک پروژه است** (نیازمندی‌ها §36.1) — کاهش‌یافته با: Resolver مرکزی، تست واحد + یکپارچگی در فاز ۲ پیش از وجود هر ماژول کسب‌وکار، و قانون «هیچ Query بدون Scope».
5. **ریاضیات مرز سال جلالی** — اعتبارسنجی وام به استخراج درست سال جلالی وابسته است؛ تست‌های واحد اختصاصی حول مرزهای نوروز نوشته شود.
6. **create-next-app و پوشه frontend/ از پیش پرشده** — پوشه frontend/ از حال حاوی DESIGN.md، AGENTS.md و src/fonts است؛ فاز ۱ Next.js را در پوشه موقت اسکفولد و سپس ادغام می‌کند (در Spec فاز ۱ مستند می‌شود).

## ۴. تعریف پایان پروژه (در سطح کل)

پیاده‌سازی زمانی تمام است که: هر ۱۱ دروازه فاز گذشته باشد؛ معیارهای موفقیت §35 به‌صورت قابل نمایش برآورده شده باشد؛ کارفرما بتواند با پیروی از `docs/runbooks/bring-up.md` (تولید فاز ۱۱) کل برنامه وب را شخصاً روی VM بالا بیاورد و کارکرد همه ماژول‌ها را در هر دو زبان انگلیسی و فارسی مشاهده کند.
